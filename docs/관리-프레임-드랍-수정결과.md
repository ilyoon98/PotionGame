# 관리 창 프레임 드랍 수정 · 2026-10-19

관리 창을 열어 둔 동안 0.2초마다 숨은 탭을 포함한 전체 행을 갱신하고 있었다. 격리된 Godot 4.6 headless 측정에서 한 번의 갱신에 약 127~136ms가 걸렸다. 목표 30FPS의 프레임 예산은 약 33ms다.

## 변경

- `management_panel.gd`: 주기적 갱신은 선택한 탭의 행·정렬·추천·계약 요약/훈련만 처리한다. 수주 관리가 열리면 해당 화면과 헤더만 갱신한다. 초기화, 탭 전환, 구매 후 명시적 전체 갱신은 기존 동작을 유지한다.
- 포션 게이지는 매 프레임 전체 포션 설명, 구매 조건, 재료, 생산 우선순위를 만들지 않고 실제 제조 시간과 재고를 읽는다. 미발견 레시피 마스킹과 이전 저장의 재고 집계 방식은 유지한다.
- `centered_button_content.gd`: 버튼 여백을 매번 최소값으로 되돌린 뒤 같은 중앙 여백을 재적용하던 동작을 없앴다. 실제 최종 여백이 바뀔 때만 스타일 변경 신호가 발생한다.
- `currency_text.gd`와 행 강조: 같은 아이콘 폭·테두리 값을 반복 적용해 테마와 레이아웃을 무효화하지 않는다.

게임 경제, 저장 형식, 시뮬레이션 시간, RNG, 기존 그림과 UI 배치는 변경하지 않았다. 정상 플레이 저장 파일과 실행 중인 플레이 세션에 접근하지 않았다.

## 측정과 회귀 검증

근거는 `.verification/management-performance/`에 있다. 비교값은 평균 CPU 갱신 시간이며, 수정 전은 당시의 전체 갱신, 수정 후는 실제 주기적 갱신 경로다.

| 검사 | 결과 |
| --- | --- |
| 수정 전 headless 전체 갱신 | 약 127~136ms/회 |
| 수정 후 headless 탭별 주기적 갱신 | 약 0.2~16ms/회 |
| 포션 게이지 headless 갱신 | 약 7.8ms → 약 0.4ms/프레임 |
| 실제 OpenGL 렌더링, RTX 3060 | 7페이지 모두 중앙 프레임 시간 약 33.33ms, 목표 30FPS |
| 변경 없는 전체 갱신 | 감시한 행/구매 버튼 스타일의 변경 신호 0회 |
| 숨은 탭·수주 관리 | 주기적 갱신에서 가려진 행을 건드리지 않음 |
| 선택 탭 갱신 | 모든 행 설명이 명시적 전체 갱신 결과와 동일 |
| 빠른 게이지 | 전체 Status 포션 투영과 제조·보유 값 동일 |
| 전체 게임 상태 | 관리 탐색 전후 모든 필드 동일 |
| 금액 표시 검사 | 통과 |
| 관리 통계 검사 | 563개 검사 통과 |
| 계약 UI 검사 | 226개 검사 통과 |
| 통계 저장 보존 검사 | 20회 탐색, 동일 State, 시간 누적, 격리 저장 왕복 통과 |

측정은 진행을 고정한 격리 fixture로 각 페이지를 반복 갱신한 결과이며 실제 플레이의 모든 저장·부하 조합을 보장하는 수치는 아니다. 실제 렌더링 검사에서는 sandbox의 `user://` 쓰기 제한으로 셰이더 캐시 생성 경고가 발생했지만 렌더링과 검증은 완료했다.

기존 `verify_stable_management_tabs.gd:87`의 행 높이 상한 검사는 실패했다. 수정 전 소스 사본으로 같은 검사를 실행해 같은 위치와 메시지로 실패함을 확인했다. 이 수정에서는 해당 레이아웃 기준이나 검사 기대값을 변경하지 않았다. `baseline-stable-tabs.log`와 `verify_stable_management_tabs.log`에서 비교할 수 있다.

재검증은 `tools/verify_management_performance.gd`를 `--headless` 또는 실제 그래픽 모드로 실행한다. 플레이 저장 대신 `isolated_preview`를 사용하며 로그 경로는 쓰기 가능한 절대 경로로 지정한다. `-- --full-refresh`는 명시적 전체 갱신 비용을 별도로 측정한다. 결과 JSON의 `frame_median_ms`는 수정 후 검사에서 CPU 갱신과 다음 프레임 대기를 합친 시간이다. 초기 수정 전 JSON의 같은 필드는 대기 시간만 포함하므로 전후 프레임 비교에 사용하지 않는다.

수정 코드는 게임을 정상 종료하고 다시 실행하면 반영된다.

## 실제 진행 중 끊김 후속 수정 · 2026-10-19

사용자가 느낀 끊김을 진행 중인 게임 상태로 재측정했다. 앞선 고정 상태 검사는 재고·예약 상태가 변할 때의 레이아웃 비용을 포함하지 못했다. 관리의 0.2초 목록 갱신 간격 자체는 기존 코드에서 유지되고 있었지만, 재고가 바뀔 때 `IngredientIcons.show_entries()`가 같은 레시피의 Control을 제거하고 재생성했다. 격리된 3초 진행 구간에서 포션 탭은 재료 묶음 234개, 레시피 탭은 489개를 새로 만들었고 최대 프레임 시간은 각각 64.37ms, 46.04ms였다.

후속 변경은 다음과 같다.

- 재료 ID와 순서가 같으면 아이콘·수량 Label을 유지하고 툴팁·메타데이터·실제 변경된 수량만 갱신한다. 미발견 마스킹과 레시피 구성 변경 때만 목록을 재구성한다.
- 포션·레시피의 주기적 계산은 스크롤 안에 드러난 행만 처리한다. 스크롤 이동은 다음 프레임의 갱신을 요청해 새로 드러난 정보가 이전 값으로 남지 않게 한다. 명시적 전체 갱신은 유지한다.
- 제조·판매·채집의 남은 시간은 진행 게이지와 함께 매 프레임 읽는다. 표시 숫자가 같은 프레임에는 텍스트를 다시 적용하지 않는다. 시뮬레이션을 UI에서 진행하거나 시간을 예측해 보상을 지급하지 않는다.

`tools/verify_management_animation.gd`는 실제 게임과 같은 advance/interface/process 경로에 고정 1/30초를 공급하며 5페이지에서 각 90프레임을 렌더링한다. 비교용 시뮬레이션과 전체 상태가 동일한지 확인한다. 재현용 fixture만 사용하며 정상 플레이 저장은 읽거나 쓰지 않는다. 근거는 `.verification/management-animation/before-Windows.json`, `after-Windows.json`, `after.log`다.

| 진행 중 측정 | 수정 전 | 후속 수정 후 |
| --- | --- | --- |
| 포션 CPU 95백분위 | 22.82ms | 3.77ms |
| 레시피 CPU 95백분위 | 34.47ms | 2.26ms |
| 포션 최대 프레임 시간 | 64.37ms | 33.54ms |
| 레시피 최대 프레임 시간 | 46.04ms | 33.54ms |
| 두 탭의 재료 Control 생성 | 234개 / 489개 | 0개 / 0개 |

5페이지 모두 중앙 프레임 시간은 33.33ms였고 검사 구간 전체 최대는 33.60ms였다. 목표 30FPS와 기존 목록 갱신 간격은 유지했다. 이 수치는 동일 장치의 짧은 격리 시나리오 결과이며 모든 부하의 최대 지연을 보장하지 않는다.

추가 검증은 모두 통과했다: 목록 갱신 사이 0.12초 동안 매 프레임 제조 게이지 증가 및 남은 시간 변경, 화면 밖 행 생략과 스크롤 직후 갱신, 매 프레임 UI 전후 전체 상태 동일, 36종 재료 표시/노드 재사용 540검사, 관리 성능 회귀, 계약 UI 226검사, 통계 564검사. GPU 실행의 셰이더 캐시 쓰기 제한은 앞선 검사와 동일하다.
